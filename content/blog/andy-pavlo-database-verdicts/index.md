这期 The MAD Podcast 中，Matt Turck 采访了 CMU 数据库教授 Andy Pavlo。他们聊到图数据库是否必要、GPU 加速值不值得，以及向量数据库和 Postgres 各自会走向哪里。

Pavlo 已经加入 ClickHouse，负责新成立的 ClickHouse Labs。Matt 在节目里也披露，他所在的 FirstMark 是 ClickHouse 的投资方。这次对话也谈到分析与事务系统如何结合，以及他为什么去企业做研究。

## 为什么他说图数据库是个坏主意

聊到 Agent 的上下文层是否需要图数据库，Pavlo 说：「我对图数据库有很强烈的意见。我觉得你不需要它。」他没见过基准测试证明，原生图数据库能胜过具备相应 SQL 或 API 支持的关系数据库。

这里有个条件：图遍历要留在服务器端完成。逐个取回节点，再由客户端决定下一步走哪里，来回通信会拖慢查询。他说，采用这种遍历方式，图数据库确实会赢；关系数据库得具备相应的执行优化。

在他的解释里，图遍历可以转成表的自连接，研究中已有高效实现，ClickHouse 和 DuckDB 也采用了其中一些优化。SQL:2023 加入了属性图查询，Oracle 已经支持，查询可以直接在服务器端完成。

他还在 Hacker News 上和人打过赌：如果到 2030 年，图数据库市场超过整个关系数据库市场，他就穿上写着 I love graph databases 的 T 恤，以这身打扮出现在驾照照片、大学证件和个人网站上，直到去世。

谈到这场赌局，他说现在是 2026 年，还有四年，他认为这件事不会发生。回到选型，他给出的判断依旧是：「图数据库，我认为是个糟糕的主意。没有理由让人真的想用它。」

## GPU 数据库要先算性能和成本

聊到 GPU 数据库，他先解释，这类系统把查询执行交给 GPU。数据库专用硬件并不新鲜，1970 年代就有人造机器执行排序和查询算子，到 1980 年代初，这条路线逐渐失去了优势。

因为设计和制造专用硬件需要时间，等新机器造出来，Intel 或 Motorola 已经推出了下一代 CPU。2010 年代又出现一批 GPU 数据库，当时的大问题是数据得放进显存，经 PCIe 搬运数据太慢。

近来 Nvidia 收下了一些 GPU 数据库公司，包括 HeavyDB。Pavlo 也当过 Voltron Data 的顾问。他说：「Nvidia 显然在推动这件事，因为这样能卖出更多 GPU。」GPU 本身昂贵，整套数据库都跑在 GPU 上，短期是否划算，他还没有答案。

他听到的情况也不一致。微软已有用 GPU 加速分析的云服务，另一家大型数据库公司算过经济账，决定不值得做。他也提到研究中的性能收益：「如果性能提升相当大，也许就有意义。」

他的学生在威斯康星大学做的 Sirius 项目，尝试让现有数据库把查询交给 GPU 执行，包括 DuckDB。ClickHouse 也在研究类似方向，但数据布局怎么转换、内存怎么组织和共享，都还需要验证。

## 向量数据库会继续存在，但有两条出路

聊到 RAG，Pavlo 说，很多向量数据库在 2016 年左右就存在了，后来聊天机器人让它们的用途变得明显。「护城河并没有那么大，它只是一个索引。」一年之内，几乎每家数据库厂商都加上了向量索引。

他提到自己知道经营得很好的一家公司：Turbopuffer。在他看来，它高度专注于向量检索，性价比远好于其他厂商。「我不认为向量数据库会消失。我认为它们会向两个方向演变。」

一条是成为类似 Postgres、MySQL 的通用系统，直接保存业务原始记录和对应的向量，承担主数据库的职责。另一条是像 Elasticsearch，保留一份从业务数据库同步来的副本，专门提供检索。

如果走后一条路线，它们可以作为额外的检索系统继续存在。如果要追求最好的向量检索性能，有些场景还是会选择专用系统。不过，有人预测 Postgres 会被向量数据库取代，他不认同：「这不会发生。」

## Agent 为什么常推荐 Postgres

聊到模型替人选数据库，Pavlo 说：「如果我在做一个新应用，它现在多半会推荐 Postgres。」他把原因归到预训练素材：模型学到的，是人们已经写过的内容。这个判断来自过去的使用经验，他也有一阵子没再尝试了。

如果把需求说得更具体，答案会改变。嵌入式设备可能推荐 DuckDB 或 SQLite，只需要键值存储可能推荐 RocksDB。做分析时，还要继续说明工作负载、数据和预算，才会得到更细的建议。

已有两家数据库公司来问他，怎样让 Agent 优先推荐自家产品，排在 Postgres 前面。他回答：「这不是我做的事，这不是研究。别来找我，去找构建模型的人。」他把这种推荐竞争比作 SEO。

他自己也被训练素材困扰过：问数据库问题，模型却把他的课程材料引用回来。即使要求别引用 CMU，它也可能改引另一所大学；仔细一看，还是那所大学复用的、他自己公开的课件。

## 接上 MCP，离正确查询还有多远

Matt 问到数据库厂商纷纷提供 MCP server，Pavlo 赞成有一个标准接口。在他的类比里，MCP 基本上是个 REST 接口：它规定请求怎么表达，接收请求的系统再把它转换成自己的 API 或 SQL 调用。

他认为在网络上传输人类可读文本有些低效，二进制协议可以做得更好，但当前方式已经够用。「它不是解决世界上所有问题的银弹，它只是一个接口。」请求从 MCP 进来，数据库仍得判断谁在访问、要做什么、有没有权限。

聊到自然语言转 SQL，他一直怀疑部分学术研究里的成绩。很多框架用 Spider 等知名基准做测试，而他认为模型已经在这些数据上训练过。「它们当然会把正确答案复述出来。」

他在录制前一天与一家大型银行的人聊过。按对方的介绍，最初采用现成方案，再做一些内部改进，准确率大约六成。后来投入数年、数百万美元，补充更丰富的语义层和上下文，才提高到百分之九十九点五。

他据此说：「如果肯花时间，提供正确的语义层和上下文信息，这件事现在是可行的。」但那是有充足资源的银行；随便下载一个现成工具，还达不到同样的准确率。他认为，需要让 Agent 掌握足够信息，才能从问题推导出正确 SQL。

## 同时做事务和分析，为什么很难合成一个系统

Matt 提到，ClickHouse 增加了托管 Postgres，Databricks 收购 Neon，Snowflake 收购 Crunchy Data。Pavlo 认为数据库公司应该同时提供事务和分析能力，至于两者该不该放进同一套系统，还得另谈。

他猜，从分析数据库起步，先获得客户，再补事务数据库，可能比反过来更容易。Databricks 和 ClickHouse 都走了这条路。他也承认自己因加入 ClickHouse 而有偏向，无法证明这种商业路径一定更好。

两家公司在架构上有不同选择。ClickHouse 目前提供独立服务，把 Postgres 数据快速送进分析引擎。按他介绍，Databricks 的方案允许分析引擎直接读事务数据，避免维护两份副本。

两种引擎共用一份数据的想法早就有了。他当过顾问的 Splice Machine 在 2010 年代就做过类似尝试。Oracle 和 SQL Server 则可以分别维护行存与列存，再通过内部机制同步。

这类混合系统没有广泛普及，还有组织上的原因。「他们不想要一个事务处理做得还行、分析也做得还行的系统。他们要最好的事务系统。」做分析的人也有同样的要求，技术之外还有销售和采用的难题。

## 关系模型会留下，SQL 可能变成汇编

Matt 问数据库行业是否显得停滞，Pavlo 说，相比 AI，什么都会显得慢。他不认为数据会发生某种巨变，迫使大家扔掉已经掌握的数据库知识；关系模型仍是表示数据的基础，可以继续改变它的实现。

他拿算术作比：「你不会发明一种新的算术，去取代一加一等于二。」提升性能、降低硬件成本，仍然有很多工作能做。他还没看清 Agent 的工作负载是否足够特殊，需要改变数据库架构。

谈到 SQL，他说：「总有人想取代 SQL。我觉得这可能是徒劳的。」但自然语言转 SQL 如果继续奏效，用户未必需要亲手写查询。「SQL 可能会变得像汇编语言。」就像现在很少有人手写汇编，SQL 可以由工具生成。

他也设想过，未来每个应用可以用 Agent 写出高度专用的数据库。现在一些系统已经在查询的局部环节做代码生成和即时编译。进一步做到高度专用，并让它可持续，可能成为今后的研究问题。

## ClickHouse 的架构之外，还有什么值得做

聊到 ClickHouse，Pavlo 回忆，2016 年它发布时，他知道做一个数据库有多难，却不知道有哪个开源分析引擎同时具备列存、向量化执行、压缩和后台合并。「我以为它是假的，结果它是真的。」

这些方法如今已不新鲜。按他的介绍，相关思想来自 Snowflake，也能追溯到更早的 MonetDB/X100 和 VectorWise。DuckDB、Polars 等系统也有相似架构，ClickHouse 多年来一直继续优化性能，并扩大能支持的工作负载。

所以他谈产品时，也看用户界面、开发者体验、数据接入和互操作。Snowflake 的成功有一部分来自这些工作。「ClickHouse 跟其他系统在最底层其实很相似，但周围的东西很重要。」内核仍有改进空间，周边能力也能扩大产品的使用范围。

至于为什么加入 ClickHouse，其他公司曾邀请他做工程师，或者只允许他做缩水的研究。ClickHouse 愿意让他建实验室，他反问对方是否明白，做研究可能得不到预期结果，对方仍然愿意继续。

在那里，他可以用真实工作负载和生产系统验证研究，再把有效的方法推出去，不必写完论文后等待别人采用。他说：「如果这个想法确实有意义，我们就能在很短的时间里把它推出去。」
